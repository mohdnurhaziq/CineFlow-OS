# System consistency audit, 26 November 2026

A read-only look across the back-end, the UI and design, the wording, and the docs. Nothing was changed.
Every finding below was checked in the code. Numbers come from searching the source, so treat them as
"about this many", not exact. This is a **static review**: I did not click through every screen on every
device, so the visual items are about code and styles, not what each page looks like today.

Severity: **A** = fix soon (a real risk or bug), **B** = consistency debt (works, but drifts), **C** = polish.

---

## A. Fix soon

### A1. Booking lookup has no rate limit, and tracking codes are guessable (back-end, security)
- `lookupMyBooking` (`lib/actions/my-booking.ts`) is public. It opens a booking with the pair
  *email + tracking code* and has **no rate limit**. Every other public entry point has one (sign-in, register,
  reset, invite request, slot hold, upload).
- The code is `BK-<studio>-<time in base 36>-<4 random characters>` (`lib/actions/checkout.ts:111-112`,
  `lib/actions/admin-bookings.ts:127`). The time part can be worked out from when the booking was made.
  The random part uses `Math.random()` (not secure) and has about 1.7 million combinations.
- Someone who knows a client's email could try codes without limit and reach the booking, its invoices and
  its gallery link.
- **Suggestion:** rate-limit the lookup per email and per visitor (reuse `isRateLimited`), and make the random
  part longer with `crypto.randomBytes` (for example 8 characters). Old codes keep working.

### A2. Text is too faint on the dark theme (UI, accessibility)
- Muted grey `text-zinc-500` is used about **370** times. On the dark surfaces it measures **3.7 to 4.1:1**; the
  accessibility minimum for normal text is 4.5:1. `text-zinc-600` (31 uses) is only **2.3 to 2.6:1**.
- About **350** places use text of 10 pixels or smaller, which makes the faint colour harder still.
- The landing page footer was already fixed to `zinc-400` (7.3:1). The rest of the app was not.
- **Suggestion:** one muted-text token at `zinc-400`, no text below 11-12px, and swap the two greys across
  the app in one pass (a search and replace, then a visual check).

### A3. Dialog close buttons have no name and a tiny target (UI, accessibility)
- At least **15 dialogs** (calendar, CMS, frames, proposals, services…) close with a bare "X" button that has no
  `aria-label` or `title`, so a screen reader says only "button". The button is `p-1`, about 24 pixels, well
  below the 44-pixel touch target used elsewhere (the session menu and landing page use it).
- **Suggestion:** one shared `DialogCloseButton` (label "Close", 44px target) used by all dialogs.

### A4. "Today" is the UTC date in several places (back-end and UI, dates)
- Malaysia is UTC+8. `new Date().toISOString().slice(0, 10)` gives the *previous day* between midnight and 8 am.
  It is used in about 15 places, for example the project list's next shoot day
  (`app/[tenantSlug]/admin/projects/page.tsx:101`), the project workspace (`project-workspace.tsx:169`), the plan
  banner, the default invoice due date, and the calendar dialogs' default dates.
- The right tools already exist in `lib/slot-time.ts` (`studioNow`, `slotDateKey`, `formatStudioDate`,
  `isSlotInPast`). The booking-reschedule list is safe because it also uses `isSlotInPast`.
- **Suggestion:** replace every `toISOString().slice(0, 10)` for "today" with `studioNow().dateKey`.

### A5. Client emails are not always lowercased (back-end, data)
- Most sign-up paths lowercase the email. `lib/bookings/project-promotion.ts:143-151` does not: it looks up and
  creates the client with the raw email from the booking (`booking.clientEmail`), and the public booking
  path (`lib/actions/booking.ts:202`) stores it raw.
- The database rule is "one account per email per studio" (`@@unique([tenantId, email])`) and it is
  **case-sensitive**, so `Maya@x.com` and `maya@x.com` can become two accounts.
- The code already works around old mixed-case rows in three places (`new Set([lower, raw])`), a sign that
  the data was never cleaned.
- **Suggestion:** lowercase and trim once, in the shared schema, and run one migration that lowercases existing
  emails (merging any real duplicates by hand first). Then the workarounds can go.

## B. Consistency debt

### B1. Five ways to show money (UI and back-end)
- Shared helper `formatMoney` / `currencySymbol` in `lib/money.ts` exists, but:
  - four components rebuild it as `currency === "MYR" ? "RM " : "$"` (`booking-intake-modal`, `cinema-slot-grid`,
    `admin-verification-console`, `cash-payment-form`). Any other currency code would show "$".
  - `print-button.tsx` prints `MYR 150.00`, the visualizer prints `MYR 150.00`, everywhere else prints `RM 150.00`.
  - `super-admin-view.tsx` and `super-admin.ts` hard-code `RM`, and some amounts use the browser's own locale
    (`toLocaleString(undefined, …)`), so the number format can differ per visitor.
  - the client dialog falls back to the text `"RM 0.00"`.
- **Suggestion:** everything goes through `formatMoney`. Fix the symbol for MYR once, and delete the local copies.

### B2. Dates: no shared formatter, mixed styles and zones (UI)
- About 24 uses of `toLocaleDateString`: **13 in `en-GB`** (26 Nov 2026), **8 in `en-US`** (Nov 26, 2026), 1 in
  `en-CA`, and one with the visitor's own locale. A Malaysian product should use one.
- Four local `formatDate` functions (client dashboard, admin client page, booking lookup, whatsapp) plus ad hoc ones.
- Some have no `timeZone`, so a date can shift depending on where it is formatted: the payment email's session
  date (`lib/payments/settle.ts:217`), the invoice due date in `admin-invoices.ts:143`, the booking dialog, the
  gear window, and the booking lookup.
- `formatSlotDate` in `lib/slot-time.ts` already defaults to `en-GB` and Malaysia time.
- **Suggestion:** one `formatDate`/`formatDateTime` in `lib/slot-time.ts` (`en-GB`, studio time zone) and use it
  everywhere.

### B3. Docs and defaults still say the old domain, plans and currency (docs)
- Code defaults and examples still use **`cineflow.app`**: `lib/env.ts:8`, `lib/domain-name.ts:11`, `.env.example`
  (domain, URL and `noreply@cineflow.app`). The live domain is `cineflow-os.my`. If a setting is missing, links in
  emails would point at the wrong site.
- `docs/03` says **18+ models**; the schema has **35**. It also says currency default `USD` (the schema default is
  still `USD`, while sign-up is MYR-only) and lists tiers `STARTER`, `PRO`, `STUDIO_UNLIMITED`.
- Docs 02, 06 and 07 and the README use `cineflow.app`, "Pro Studios", and `superadmin@cineflow.app`.
- **Three plan names exist:** the codes (`STARTER`/`PRO`/`STUDIO_UNLIMITED`), the customer names (Solo / Studio /
  Production), and the old doc names. Nothing wrong in the code, but a newcomer cannot tell which is which.
- **Suggestion:** change the defaults to `cineflow-os.my`; refresh docs 02, 03, 06, 07 and the README; add one line
  to doc 03 mapping code → name; decide whether the `USD` schema default should become `MYR`.

### B4. Wording: several names for the same thing (UI/UX copy)
- **Sign in:** "Sign in" on most pages; "Studio Login" and "Client Login" in the studio footer and one error
  message (`client-auth-panel.tsx:181`); "Studio Login" on the admin bar. Also "Sign Out" (title case) in one
  place and "Sign out" in the rest.
- **The client's photos** are called *Gallery* (~310 mentions), *Vault* (~50, including routes), *Deliverables*
  (~90) and *Project*. "Vault" and "Deliverables" are internal words that clients can see.
- **Client vs customer:** "client" is standard, but "customer" appears about 38 times (for example "Book for
  customer", "customer's contact").
- **Suggestion:** a short wording guide (one word each for sign in, sign out, the photos, the person), then a search and fix.

### B5. The design system is only partly used (UI)
- **Buttons:** about **437 hand-made `<button>`** against about 171 that use the shared `Button`/`buttonVariants`.
- **Inputs:** **202 hand-made `<input>`**, 52 `<select>`, 21 `<textarea>`. The shared `Input` component has **0 uses**
  (the file is dead code).
- **Surface colours** are typed as raw hex, not tokens: `#121215` (162 uses), `#0d0d10` (104), `#09090b` (41),
  `#18181b` (33), then `#15151a`, `#16161b`, `#0b0b0e`, `#151518`, `#0c0c0f`… Several near-identical darks.
- **Corner radius** mixes `rounded-lg` (~450), `-xl` (~360) and `-2xl` (~230) with no rule for cards vs controls.
- **Page titles:** 33 files write their own `<h1>`, with 8 different size combinations, while 51 files use the
  shared page header.
- **Suggestion:** pick tokens for 3 surfaces, 3 radii and 3 heading sizes; make `Button`, `Input`, `Select`,
  `Textarea` the only way to build them; migrate area by area (no big-bang).

### B6. Error and loading screens are patchy (UI/UX)
- `error.tsx` exists only for the platform pages `(saas)`. **Studio sites, the admin, and the client account have
  none**, so a crash there falls back to the global error page, which replaces the whole screen (no header, no
  way to retry in place).
- `not-found.tsx` exists only at the root, so every missing page looks the same, whichever area you are in.
- The client account has no `loading.tsx` of its own (it borrows the studio one).
- `app/(saas)/create-studio/page.tsx` has no title of its own (it is a client page), so the browser tab shows the
  generic site title. Every other page has one.
- **Suggestion:** an `error.tsx` per area (admin, account, studio site) in that area's style, a not-found per area,
  and a title for the sign-up page (a small server wrapper).

### B7. Two result shapes from server actions (back-end)
- Most actions return `{ success: false, error: "<message>" }`. Others (booking, checkout, booking lifecycle)
  return `{ success: false, error: "CODE", message: "<text>" }`. Screens therefore read `error` in some places
  and `message` in others.
- **Suggestion:** one shared result type (`ok` or `{ error: { code, message } }`) over time, starting with new
  actions. No rewrite needed now.

### B8. Phone and password rules differ between forms (back-end/UX)
- **Phone:** minimum 6 characters in six places (`booking`, `checkout`, `admin-bookings`, `client-auth`, `print-orders`,
  `admin-clients` by digits), while a screen check uses 7. No format is applied, so "+60 12-345 6789" and
  "0123456789" are stored as different values. This hurts search, duplicates and the WhatsApp links.
- **Password:** reset and client register cap at **72 characters** (the bcrypt limit). Studio sign-up (`lib/validations/onboarding.ts`)
  has no cap, so a very long password is silently cut at 72 bytes. The cap counts characters, not bytes.
- **Suggestion:** one shared phone schema (normalise to `+60…`), one shared password schema (8 to 72 bytes).

### B9. The Privacy Policy lists fewer browser-storage items than the app uses (docs/compliance)
- The policy mentions one random booking code. The app also keeps the held slot, the calendar view choice, the
  "invite" banner dismissal, the cart and the sign-up wizard answers (`localStorage`/`sessionStorage`).
- Their names use three styles: `cineflow.calendar.view`, `cineflow_session_id`, `cineflow:create-studio`.
- **Suggestion:** one naming style (`cineflow:…`), and one more line in the policy ("preferences and
  in-progress choices"), since the policy says it lists what is stored.

## C. Polish

- **Dead code:** 6 unused components: `account/logout-button`, `showcase/client-testimonials`,
  `showcase/studio-pedigree`, `ui/badge`, `ui/card`, `ui/input`. 24 lint warnings (unused values).
- **Sign-out is written several times:** 8 components call `logoutAction` with their own handler (admin bar, portal menu, public menu, booking panel, auth panel, invite panel, "Your studios", and one unused button). Only 3 of them (admin bar, portal menu, public menu) use the custom-domain sign-out detour that also clears the platform cookie; the booking panel, auth panel and invite panel do not. They may not need it, but it is worth checking on a studio's own domain. A shared `useSignOut()` would keep them identical.
- **Demo data is in USD** (the seed and the Lumina studio show `$3,650.00`) while the product sells in ringgit.
  Fine for tests, but screenshots from dev look off-brand.
- **Auth forms:** six similar forms (studio, client, platform, super-admin, reset, forgot password) each carry their own
  validation and error text (about 1,100 lines). A shared field and error pattern would keep wording identical.
- **Schema default plan** is `PRO` (shown as "Studio"), while the sign-up wizard offers a choice. Harmless, but surprising.

## What looked consistent (so you know it was checked)

- **Access control:** every action goes through the same checks, and tests list each action with its allowed roles.
- **Slugs:** the reserved-address list is thorough (platform names, mail names, a studio's own page names, and now `privacy` and `terms`).
- **Images:** every `<img>` has `alt` text.
- **Sign-in protection:** the shared limits cover sign-in, reset, register, invite requests, uploads and slot holds.
- **Passwords:** hashed the same way everywhere (bcrypt, cost 10).
- **Code hygiene:** no `TODO`/`FIXME` and no `console.log` left in source.
- **Studio time zone:** one setting for the whole app, with helpers for it.

## Suggested order (to discuss)

1. **A1** (booking lookup limit and stronger codes) and **A5** (email case): small, and they protect data.
2. **A4** (UTC "today") and **B2** (one date formatter): one change fixes both.
3. **A2**, **A3**, **B1** (colours, close button, money): quick, visible wins.
4. **B3** (domain and docs refresh) before you share the repo or onboard anyone.
5. **B5** and **B6** (design tokens, error screens): bigger, do them area by area.
6. **B4**, **B7**, **B8**, **B9**, then the polish items.
